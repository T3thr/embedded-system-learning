## หน้า 1 — ชื่อเรื่อง (0:00–0:15)

สวัสดีครับ ผมธีรภัทร ภู่ระย้า รหัส 66362416 นะครับ วันนี้จะมาเล่าเรื่อง **Interrupt Mechanism** หรือกลไกการขัดจังหวะครับ

อยากให้โฟกัสสองอย่าง หนึ่งคือ interrupt คืออะไรกันแน่ สองคือพอมันเกิดขึ้นแล้ว CPU จัดการยังไงตั้งแต่ต้นจนจบ แล้วกลับไปทำงานเดิมได้โดยไม่พัง

**เช็คแหล่งอ้างอิง:** กรอบเรื่อง "ระบบฝังตัวประกอบด้วย CPU/memory/I-O และมี timer, interrupt รวมอยู่บนชิปเดียว" มาจาก Lecture 1 หน้า 9 บรรทัด 177–188 (ผังไมโครคอนโทรลเลอร์) ไม่ใช่หน้า 2–4 ซึ่งเป็นแค่นิยามทั่วไปของ embedded system — ถ้าอาจารย์ถามอ้างหน้า 9 ให้ถูกจุด

## หน้า 2 — นิยามและ 4 คุณสมบัติ (0:15–0:50)

เอาแบบง่ายๆ ก่อนนะครับ ปกติ CPU รันโปรแกรมของมันไปเรื่อยๆ ทีนี้ถ้ามีอุปกรณ์ภายนอก เช่น timer หรือ peripheral ต้องการให้ CPU มาสนใจ มันจะส่ง request เข้ามา CPU ก็หยุดงานที่ทำอยู่ชั่วคราว กระโดดไปทำ **ISR** หรือ Interrupt Service Routine ก่อน แล้วค่อยกลับมาทำงานเดิมต่อ — นี่แหละคือ interrupt

ลองนึกภาพง่ายๆ เหมือนตอนเรานั่งทำการบ้านอยู่แล้วมือถือเด้งแจ้งเตือนขึ้นมา เราก็หยุดงานตรงนั้นไว้ก่อน ไปดูแจ้งเตือน จัดการเสร็จแล้วค่อยกลับมาทำการบ้านต่อจากบรรทัดเดิม — CPU กับ interrupt ก็ทำงานคล้ายๆ แบบนี้ครับ ต่างกันตรงที่ CPU ต้อง "จำ" ให้แม่นว่าตัวเองค้างอยู่ตรงไหนก่อนจะไปรับแจ้งเตือน

สไลด์บอกไว้ 4 คุณสมบัติ อย่างแรก **event-driven** คือ control flow เปลี่ยนเพราะมี event ไม่ใช่โปรแกรมเรียกเอง อย่างที่สอง **state-preserving** คือต้องเก็บ state ไว้ก่อน ไม่งั้นกลับมาทำงานเดิมไม่ได้ อย่างที่สาม **vectored** คือมีตำแหน่งหรือ vector table บอกว่า handler ของแต่ละ interrupt อยู่ตรงไหน สุดท้าย **priority-aware** คือถ้ามีหลาย interrupt เข้ามาพร้อมกัน ต้องมีลำดับความสำคัญตัดสินว่าใครไปก่อน

จุดที่ต่างจาก polling ชัดๆ คือ polling ต้องให้ CPU คอยวนถามอุปกรณ์ตลอดเวลาว่า "พร้อมหรือยัง พร้อมหรือยัง" เหมือนเรานั่งเช็คมือถือทุกสิบวินาทีทั้งที่ยังไม่มีแจ้งเตือนเข้ามาเลย เสียเวลาไปเปล่าๆ Mazidi อธิบายไว้ในบท interrupt ของ AVR ว่าวิธี polling แบบนี้เปลืองรอบการทำงานของ CPU เพราะบางทีเช็คไปก็ยังไม่มีอะไรจะบอก

**เช็คแหล่งอ้างอิง:** นิยาม interrupt/ISR/polling — Mazidi, *The AVR Microcontroller and Embedded Systems* หน้า 375–376 (บท interrupt programming) [อ้างในสไลด์ [1]]. 4 คุณสมบัติเป็นการสรุปจากข้อความบนสไลด์เอง ไม่ใช่คำต่อคำจากหนังสือเล่มเดียว ถ้าถูกถามให้บอกว่า "สรุปจากภาพรวมของกลไก ไม่ใช่นิยามที่ยกมาทั้งประโยค"

## หน้า 3 — สามระยะการทำงาน (0:50–1:40)

ทีนี้มาดูเป็นขั้นตอน สไลด์แบ่งไว้ 3 phase

Phase แรก **Request** — เกิด event ที่อุปกรณ์ แล้วมันตั้ง flag ไว้ ตอนนี้คำขอยังไม่ได้รับบริการ เรียกว่าอยู่ในสถานะ pending

Phase สอง **Entry** — CPU เช็คก่อนว่าคำขอนี้ enable ไว้รึเปล่า ถูก mask บล็อกมั้ย priority พอมั้ย ถ้าผ่านทุกเงื่อนไข ก็เก็บ context ที่จำเป็น แล้วใช้ vector หาตำแหน่งเริ่มของ handler

Phase สุดท้าย **Service กับ Return** — ISR จัดการสาเหตุที่ทำให้เกิด interrupt เช่น อ่านค่าที่อุปกรณ์ส่งมา หรือเคลียร์ flag ที่ค้างไว้ แล้วคืนค่ากลับ ให้โปรแกรมทำงานต่อจากจุดเดิม เหมือนตอนเราปิดแจ้งเตือนแล้วกลับมาทำการบ้านต่อจากบรรทัดที่ค้างไว้พอดี ไม่ใช่เริ่มใหม่ทั้งหน้า

ขอยกตัวอย่างจริงจาก 8051 ที่เราเรียนกันในวิชานี้ครับ lecture 3 บอกว่า stack เก็บ return address ของทั้ง ISR และ subroutine โดย SP เป็นตัวชี้ตำแหน่งบน stack พอ ISR จบงาน มันใช้คำสั่ง **RETI** ไม่ใช่ **RET** ธรรมดา เพราะ RET แค่กลับไป main program เฉยๆ แต่ RETI จะกลับไปที่เดิม พร้อมเปิด interrupt ให้ทำงานได้อีกครั้ง ตามที่ lecture 4 อธิบายไว้ตรงส่วน RET กับ RETI ตรงนี้เป็นจุดที่หลายคนสับสนได้ง่ายเวลาเขียนโค้ด 8051 ครับ ถ้าใส่ RET ผิดที่ ระบบจะไม่ยอมกลับมารับ interrupt ตัวใหม่อีกเลย

**เช็คแหล่งอ้างอิง:** stack/SP เก็บ return address — Lecture 3 หน้า 9 บรรทัด 503–509 ("Stack is used to store return address during ISRs and Subroutines", "Top of stack is pointed by SP register"). RET vs RETI — Lecture 4 หน้า 28 บรรทัด 1398–1411 ("RET — used with normal subroutine", "RETI — used with ISR ... return back to main program + Enable Interrupt by making EA = 1"). กรอบ 3 phase (Request/Entry/Service-Return) เป็นการสังเคราะห์จากลำดับที่ปรากฏร่วมกันใน Mazidi และสไลด์เอง [2][3]

## หน้า 4 — เงื่อนไขที่ทำให้ทำงานถูกต้อง (1:40–2:15)

คำถามคือ อะไรทำให้ interrupt ทำงานถูกต้อง สไลด์สรุปไว้ 3 เงื่อนไข

หนึ่ง **qualify** — คำขอต้องผ่าน enable, mask, priority ก่อนถึงจะไปต่อได้ ใน 8051 มีบิต **EA** เป็นตัวเปิดปิด interrupt รวมทั้งระบบ ถ้า EA เป็น 0 ต่อให้ enable ตัวย่อยเปิดไว้ก็เข้า ISR ไม่ได้ ส่วน **IE** กับ **IP** เป็น register ที่ใช้เปิด/ปิดและจัดลำดับความสำคัญรายแหล่ง ซึ่งจากตารางใน lecture 3 IE อยู่ที่ address A8H และ IP อยู่ที่ B8H

สอง **preserve** — ต้องรักษา context ให้ถูกต้อง เพราะถ้า ISR ไปแก้ register ที่โปรแกรมเดิมยังใช้อยู่ แล้วไม่เก็บไม่คืนให้ครบ โปรแกรมเดิมจะพังทันทีที่กลับมาทำงานต่อ

สาม **complete** — ISR ต้องจบงานให้ถูกวิธี อย่างที่บอกไปคือใช้ RETI ไม่ใช่ RET แล้วก็ควรทำงานให้สั้นที่สุดเท่าที่จำเป็น เพราะถ้า ISR ทำงานนานเกินไป จะไปเพิ่ม latency ให้ interrupt ตัวอื่นที่รออยู่

**เช็คแหล่งอ้างอิง:** IE=A8H, IP=B8H — Lecture 3 หน้า 12 บรรทัด 700–745 (ตาราง SFR). EA เป็น global enable ที่ RETI set เป็น 1 — Lecture 4 หน้า 28 บรรทัด 1409–1416. bounded ISR / latency-jitter — หลักการทั่วไปที่ต่อยอดจากกรอบ enable/mask/priority บนสไลด์ [2][3][4] ไม่ใช่ตัวเลขของชิปใดชิปหนึ่ง ถ้าถูกถามเลข latency เฉพาะ ให้ตอบว่าสไลด์ไม่ได้ระบุตัวเลข พูดในเชิงหลักการ

## หน้า 5 — สรุปและอ้างอิง (2:15–2:30)

สรุปสั้นๆ interrupt ไม่ใช่แค่กระโดดไปทำฟังก์ชันหนึ่งเฉยๆ แต่เป็นกลไกที่ต้องคัดกรองคำขอ เก็บ state ให้ถูก จัดการงาน แล้วกลับมาทำงานเดิมได้อย่างสมบูรณ์

ข้อมูลที่ใช้วันนี้อ้างอิงจาก Mazidi กับ datasheet ของ Microchip สำหรับฝั่ง AVR ส่วนตัวอย่าง 8051 ที่ยกมาอ้างอิงจาก lecture 3 กับ lecture 4 ของวิชานี้ครับ ขอบคุณครับ

**เช็คแหล่งอ้างอิง:** รายการอ้างอิงที่พิมพ์บนสไลด์หน้า 5 คือ [1] Mazidi et al. (2011) หน้า 375–376, [2] Microchip ATmega328/P Datasheet (2018) หน้า 33–34, [3] Yiu, *ARM Cortex-M3* (2010) หน้า 172–175, [4] Arm Cortex-M3 Generic User Guide (2010). ตัวอย่าง 8051 ที่พูดเสริมใน 3 หน้าก่อนหน้าไม่ได้อยู่ใน 4 รายการนี้ — เป็นเนื้อหาจาก lecture 3–4 ของวิชา ถ้าอาจารย์ถามให้ตอบตรงๆ ว่า "ยกมาจาก lecture ของวิชา ไม่ใช่จากสไลด์"
